#### 议题：PoWh 统计口径 4 项，请 CGC 定性

关联：`Jouleverse/workspace` PR #108（WP-3 rev10）

PR #108 修订 WP-3 统计工时的时候，发现 4 处「规范没写明」的地方。按新立的《修订体例》第 6 条，这类问题不在 PR 内自定，提交 CGC 定；PR 正文已标「待追认」，不阻塞合并。

**1. 执行发放按「月」还是按「次」算？**
规范 A-2 写「2h/月」，raw 表列头是「执行/次」。8 月 Jeff J-29 一次性补发 7 个月，按 7 × 2h ＝ 14h 记，按「2h/月」字面找不到依据（rev9 起就如此）。

先看规程本身的要求：`work-package-specs.mediawiki`（rev8）WP-3 3.4 第 1 条「确保占比 20% 的 Jouleverse 核心资产按照本规范每月统计和分发（全额发出）」，3.5 质量要求「次月发放上月激励，最多延迟不超过 2 个月」。即规程要求的是**按月执行**，允许的延迟上限为 **2 个月**。7 个月一次性补发已远超这个上限，属于拖欠累积，不是正常节奏。

请定：按次累加（每次 2h × 月数）／ 维持 2h/月 ／ 暂不修订；以及 8 月这 14h 是否追溯。「按次累加」还需说明它与 3.5「最多延迟不超过 2 个月」如何并存——否则延迟越久、工时越多，工时激励与质量要求方向相反。

**2.「检查复核」是动作还是岗位？**
rev7 原文「统计与复核岗位非同一人承担」；rev10 解释为动作（不设复核岗，工时含在主管 2h 内）。这属于对既有决议读法的变更。
请定：追认 ／ 不追认。

**3. 单人配置月总包 7h 是否追认？**
rev7 只写「若统计组 1 人，激励还是原办法」，没给数值。7h 的推导依据（分项数值均出自 `work-package-specs.mediawiki`（rev8）WP-3 3.6 激励标准，即 CGC 2024-10-27 决议）：
- 统计（Excel 处统计数据）3h ＋ 协调跟踪 1h ＝ 4h
- GitHub 数据录入 2h
- 合并（含全局数据检查）1h

合计 4 ＋ 2 ＋ 1 ＝ **7h**。单人配置下没有轮值主管（轮值主管 2h/月出自 rev7 2025-12-07 决议），执行发放 2h 单列 A-2、不计入统计组总包，故统计组总包 ＝ 7h。所以 7h 是**按现行分项相加的推导值**，不是任何纪要直接给定的数。

请定：追认 7h ／ 另定数值。

**4. 单人配置下复核人的工时怎么算？**
单人时须由 CGC 指定他人复核，但现行文本里这个人没有计价出口。
J-67 表态：倾向于把轮值主管的 **2h** 给到「愿意用 AI agent 读完 PoWh 统计 playbook 并按该流程做统计核对」的人——复核有明确入口和可核验产出，谁做谁拿这份工时，而不是挂在轮值岗位上。
playbook：https://gcnmbaqf8vh8.feishu.cn/wiki/OfWZwOuw1iH9bwkiX7Ncrlulnec
请定：并入合并人 1h ／ 单独定价 N h ／ 不另计。

**附（低优先）**：rev7 条目仍写「按报名顺序轮值」，rev10 A 表已改「月初确定」。J-67 表态：2026 年 1 月以来实际做法就是月初确定，倾向于以 rev10 A 表「月初确定」为准，并给 rev7 条目补注。

**二、议题 2：检查复核是「动作」还是「岗位」——支持按动作理解**

- 激励与「做的事」挂钩，不与岗位挂钩。这是当初设统计组时就立的原则：不是对某个岗位给激励。
- 谁做的统计，激励就给统计人；谁做的复核，就是复核人。所以叫「统计人／复核人」，不叫「复核岗」。
- 据此，rev7「统计与复核岗位非同一人承担」的准确读法是「统计与复核**动作**非同一人承担」。

**三、议题 4：把复核工时开放给用 agent 做核对的社区成员——赞同，而且鼓励**

- 换一个人的 agent，运行状态不一样，就有可能发现前一个 agent 运行中的错误。这跟把 PR 甩给别人的 agent 先读一遍是同一个道理。
- 具体做法：看到 PR 直接把链接甩给自己的 agent，让它先理解、总结要点，再帮你拟回复、帮你做检查；人把握大方向即可。
- 效率差距很明显：以前靠人肉理解，两天能有一个来回就不错；现在一天能来两轮、三轮。
- 多人 agent 互动还能避开单一 agent 的盲区——一个人加一个 agent 容易有死角，换一个 agent 就换一套运行状态。
- 呼吁：第一先把 agent 装起来，第二用起来，第三多参与。门槛就是复制链接发给 agent，主要是意识要建立起来。
- 三人以上参与就形成多元讨论，可能产生一些非线性的结果，冒出创新的点子。

**四、非标上报时点（临时议题）——完成即报可以，但要约束格式**

- 截止时间仍是次月 10 日；统计本来就在 10 日之后才开始，所以 20 号报、1 号报、8 号报，没什么区别。
- 真正的风险是碎片化。要求：后续补充一律 update 原 comment，不要一条条新增上报记录。
- 10 日之前把记录更新完整即可，这样比较合理。

**五、JScan V2 迁移与投票验收（临时议题）**

**二、议题 1：执行发放按「月」还是按「次」——通过**

- 事实：8 月 Jeff J-29 一次发放 7 个月（202512–202606），按每月 2h 记 14h。旧规程有的版本写「2h/月」、有的写「2h/次」，两种写法都不够准。
- rev10 措辞：**执行发放 2h／每月每次发放；一次执行覆盖 N 个发放月份时，按 N × 2h 计。**

**三、议题 2：检查复核是「动作」还是「岗位」——方向通过，文字会后细化**

- rev7 原文「统计与复核岗位非同一人承担」。规程里真正的岗位只有统计主管、统计副主管、统计员；把「复核」也当成岗位，agent 读规程时会混淆。
- rev10 释义：复核是**动作**，不是岗位。会上无人反对。
- 微尘 J-53 补充渊源：早期复核没有单独工时，含在「检查合并 1h」里；后来设主管/副主管轮值，轮值主管两件事＝群发通知＋复核（录入前的复核），而合并 1h 里的「检查」是录入后的准确性检查。他建议会上不必抠文字，会后静下来润色。
- 我的结论：方向已明确（动作），具体表述会后组织；同时把 2h／4h／2h／1h 每块包含哪些动作细化写进规程。

**五、议题 4：单人配置下复核人的工时——方向获支持，先拆动作再定价**

- 提议：把轮值统计主管的 2h 给「愿意用 AI agent 读完统计 playbook、并按流程产出核对结果」的社区成员；有产出即拿这份工时。若招到固定搭档，则回到两人轮值分配。
- 理由：AI 把学习成本降下来了；而且实测同一 agent 自查自己统计出的数据会有盲点（小问题、与旧格式不一致），换一个 agent 复核更有效——我本人就打算用一个 agent 统计、另一个 agent 核对，再肉眼过一遍。
- 微尘 J-53 提醒：主管 2h 不只复核，还含群发通知等动作，只做其中一两项却拿全部 2h 不相称；建议先拆清动作，再决定分出多少（如 0.5h、1h）。
- 我接受这条意见：先把 2+4+2+1 每块的动作写清楚，再讨论能拿出多少工时激励外部核对。教链 J-25 支持这个方向，并鼓励大家把 agent 装起来、用起来参与。

**六、非标上报时点（临时议题）**

- 现行窗口：每月 1–10 日上报上月。若有人当月做完就报，归属哪个月没有明文。
- 我的看法：鼓励做完立即上报，但仍归属该自然月、由次月统计；像公司发薪（当月工作、次月发放），日期对得更整齐；风险是上报碎片化。
- 会上定：随时可报，截止 10 日；多次上报请 update 原 comment，不要刷多条。

- 关于「一次执行 4 个月」的两点顾虑：一是多月合并执行会挤压当月其他人的份额（几个百分点）；二是规程确实有发放时限要求——rev8 WP-3 3.5「次月发放上月激励，最多延迟不超过 2 个月」，rev9 沿用同一条，rev10 未改。按此，7 月激励应在 8 月发、最迟 10 月发，现已超期；所以不宜再按 4 个月一批积压，建议按月或最多两月一批补执行。需要说明的是：这条是质量要求、没有罚则，且延迟的源头在统计表未按时交付、不在执行人，统计侧要先恢复交付节奏。
