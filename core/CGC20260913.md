##一、 微尘 J-53 发言纪要

Jouleverse PoWh 统计流程改进提议

2026 年 9 月例会 · 提案人：统计组

一页概要:

根据过往做法与教链例会提议，经统计组内部商讨,现提出三处小改动：统一称谓、建立溯源闭环、把统计结果有误反馈意见征集迁到 GitHub。

三项均为低成本调整，目标是让每月账目做到三点：可验证、可解释、可追溯。

议题 现状 提案

##一 、 WP-6 称谓统一

费率表(岗位工作单次计量小时数)与会议纪要表格两套叫法 统一术语，三处列名逐字一致;

二、可追溯闭环

数字需来自可验证的原始留痕 GitHub 为唯一权威源，双向互链;

三、反馈与确认

确认需留痕、可回溯, 微信群只通知，常设 issue用来反馈与确认;

议题一: WP-6 称谓统一现状

同一个工作包的三项工作，在费率表与会议纪要表格、焦耳通讯发表篇幅里有两套不同叫法：

统一术语称谓（建议）:
会议预定 0.5 h/次
会议主持 2 h/次
会议发言 0.5 h/次

提案

• 统一采用纪要表格的叫法：会议预定 / 会议主持 / 会议发言。

• 费率表、会议纪要表格、raw 溯源表——三处列名必须逐字一致。

• 会议纪要模板维持现有格式（表格已含三栏），无需改动。

列名统一后，填表与核对均无需再做名词转换。

议题二: 统计结果可追溯闭环

提案：

单一真相源 + 双向互链（自 202608 起执行）层级 载体说明

采集层 :

GitHub issue 评 论 / 链 上 记 录 /会议纪要表格 原始留痕，可验证

计算层 :

raw 溯源表（GitHub） 中间计算，可复现呈现层 powhYYYYMM.md（GitHub） 最终表，反向链接回 raw;

• 双向互链：最终表指向 raw，raw也回指最终表，任一处改动都能被发现。

• 统计全流程在GitHub 完成；需要发群时直接转发GitHub 表格链接，点开即为权威源,不存在两份版本。

执行时点:

本项自 2026 年 8 月统计（即本次 608）起执行：608 全程数据自 GitHub 会议纪要、链上记录直采，计算进 raw 溯源表，成果录入主表。

议题三: 反馈与确认在 GitHub 完成

提案：通知与确认分离

• 微信群只做通知，转发 GitHub 表格链接，不承担确认职能。

• 设立一个常设 issue「PoWh 统计结果反馈与澄清」，长期沿用，不按月新开。每次定稿后在该 issue 下新增一条评论，

注明月份与表格链接；反馈与答复均在该评论下以回复形式完成。

• 反馈历史完整累积在一处，可查、可回溯，也便于新成员了解过往问题的处理口径。

• 自发群通知起 72 小时内可提出异议；满 72 小时无反馈即为确认。

• 「逾期视为确认」须写入规范并公示。

说明:

渠道特性 说明

微信群：适合触达 即时可达，但不留痕、无时间戳，无法回溯谁确认过

GitHub issue：适合确认 自带作者、时间戳、可检索，反馈与答复形成完整记录

两者各司其职：微信群负责让人看到，issue 负责留下记录。

议事原则：面向机制，不面向个人

建议确立一条原则：所有意见指向规则与数据，不指向具体的人。分歧落在规则上，而规则是可以改的。

建议的完整月度时间线

##二、 教链 J-25 发言纪要

教链(J-25)在本次 CGC 会议中的发言主要围绕两个核心议题：统计工作规范化流程和 vibe coding 互助学习课程项目。

一、关于统计规范化的建议

在微尘提出统计改进提案后，教链建议按照之前 CGC 会议讨论过的正式提案流程来推进：

创建 issue 或 PR；

考虑以文档形式还是 GEP 改进提案形式提交；

在 GitHub 创建后，社群公示，征求“粗糙共识”（rough consensus）；

公示期结束后再上 CGC 会判定是否达成共识，若达成则正式合并生效。

此外，教链补充了一个更根本的观点：术语规范化的关键问题在于 AI 辅助工作尚未真正落实。

如果会议纪要、社区工作都用 AI 来做，AI 生成的内容相对规范，问题会大大减少。

长远来看，应推动大家把 AI 用起来，人主要做把关。

二、关于机器人经验共享

当 Bataroc 询问机器人经验文档是直接共享还是让新用户从头实践时，教链认为：

共享是快捷方式，本质就是 agent 的 skill；

可以放在 GitHub 上分享，别人的机器人直接去读，实现共创、自进化、分布式进化；

机器人可以互相学习，就像人互相学习一样，这是一种知识的进化。

三、vibe coding 互助学习课程项目（重点发言）

教链提出依托现有基础设施（Openclaw和Jouleverse），发起一个 AI 编程（vibe coding）互助学习课程。

从区块链视角来看，一个词概括就是Vibe2Earn。主要设想如下：

课程模式：

非传统授课式，而是互助自学 + 社群分享；

设计一系列闯关课程，如第一课安装 OpenClaw（“龙虾”），通关后进入下一课；

每课设定时间（如两周），完成即通关，可获 WJ 激励；

主线是 AI + Jouleverse，结合区块链/Web3 实际项目实战；

学习内容包括：AI 工具搭建、GitHub 使用、文档、PR、协作、Web3 应用开发部署调试等。

激励与治理设计：

课程本身作为独立项目，向 Jouleverse 社区募集捐赠 WJ；

捐赠按比例发放课程治理代币（如每捐 1 万 WJ 发 1 个课程代币）；

持币者拥有治理权，具体化为选举权和被选举权；

持币者组成治理社区，选举产生理事会，负责指导课程后续发展；

生态基金也可参与捐赠，与个人捐赠形式相同。参与是对所有WJ持有者——无论是个人还是多签——完全开放、一视同仁的。

运营与收费：

课程本身限时免费（原定价如 498 元、1498元等等，初期限时免费）；

学员自行承担云主机、DeepSeek API 等个人费用；

未来若火爆，可延伸出收费模式等商业可能。

发起方式：

教链希望不是个人发起，而是找至少 3 人（奇数）联合发起，创建多签钱包；


三人分工：一人负责招生拉新(招生老师)，一人负责助教引导学员(助教老师)，一人负责内容策划(教研老师)；五人的话就是2-2-1；

最终现场确认 5 人参与：教链、楼兰渔夫、Bataroc、微尘、Koant。

项目定位：

课程是独立项目，与平台无直接关系；

多签钱包只是运营团队，类似 CEO 团队；理事会才是真正的治理股东结构；

目标是破圈拉新，吸引对 AI 编程感兴趣的人加入，通过实战掌握 AI 编程和 agent。

##三、 Bataroc J-67 发言纪要

Bataroc J-67发言总结（Jouleverse CGC会议 2026.09.13）

本周完成记账节点搭建（已进入投票环节，计入 POWH），参与微尘统计提案的部分讨论；8 月统计下周完成。

一、统计规范与微尘提案

支持统计组提案。WP-6 称谓统一是我用机器人统计时真实遇到的问题：同一件事在纪要里有「会议预定／会议主持／书记员」多种叫法，

机器人认不出来。建议从本次会议起固化，纪要统一使用「会议预定」「会议主持」「会议发言」，让人和机器人都只有一套映射。

议题二（raw 与总表双向互链）、议题三（反馈与确认留在 GitHub）对大家更方便；通过后由统计组在 GitHub 建讨论区落地，并引导大家使用。

二、AI Agent 实操与推广

被教链装过一次机器人才知道有多好用：统计、会议纪要（自动从 issue 提取、生成纪要、提 PR）都能做，人只负责把关合并。

社区里有一半以上的人用起来，迭代速度会快很多。

经验可沉淀成 md（本质就是 skill）放 GitHub 共享共维，新机器人直接读、少走弯路；机器人互相学习，文档、机器人、社区一起迭代。

token 成本不高，DeepSeek v4 flash 很便宜。

回应楼兰渔夫：几百个客户群的重复工作天然适合 AI，但微信加不进机器人，只能导出群聊记录，或把客户迁到飞书群。

已答应帮他在节点服务器上装机器人，同步异步均可。

三、vibe coding 互助学习课程

教链的提案很好，我很想参与，当场确认加入发起。建议先把互助学习跑通顺、验证线上需求，再谈收费等延伸。
