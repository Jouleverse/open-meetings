### 一、现状诊断（基于事实）

#### 1.1 文档定位单一，"指引"属性缺失

现行 spec 只有"定义"（这个 WP 是什么、激励标准多少），没有"操作指引"（这项工作怎么做、产出物放哪、报到哪里、要不要报）。全文只有一段"非标报告格式（暂定）"且示例过时。贡献者无法按图索骥。

#### 1.2 工作→产出物→WP 归属映射缺失，且存在多处矛盾

| # | 矛盾点 | 证据 |
| --- | --- | --- |
| 1 | **WP-13 知识库内容贡献归属，spec 与实践相反** | spec 原文："内容贡献不计入该WP，而是计入相关具体工作所属的WP（比如一篇节点搭建文档应报告到WP-7）"；但社区实践：微尘撰写《PoWh 统计操作指南》→报 WP-13（issue #13 2025-12-26）、教链 wiki 站功能开发→报 WP-13（2025.12）、本次 7 月上报教链纠正：wiki 内容贡献→WP-13 |
| 2 | **知识库 repo 指向不完整** | spec 只写 `Jouleverse/how`（how.jouleverse.com），实际还有 `Jouleverse/wiki`（wiki.jouleverse.com），PR #54 即发生在 wiki repo |
| 3 | **月度统计表列名与 spec 不一致** | 统计表列 "wp-7 节点审计"，spec 中 WP-7 是"链代码开发 Chain dev" |
| 4 | **同类型工作历史上报分类漂移** | 教链 2025.1 将 Core 打卡合约、节点审计脚本报 WP-3；2025.10-11 将 Core Vote/Governance 合约报 WP-15；JIP/JEEP 提案本次归 WP-15——同一人同类工作，月份不同 WP 不同 |

#### 1.3 标准/非标边界按 WP 整体划分，颗粒度过粗

现行文档把 WP 整体标为"标准工作包 / 非标工作包 / 混合工作包"，但每个 WP 内部实际都混有标准与非标：

* **WP-3**：标准（统计/录入/合并/执行 4+2+1+2h）+ 非标（工具开发、规范修订）
* **WP-6**：标准（预定会议 0.5h、签到 0.5h、书记员 2h）+ 主题发言（非标，但按规则报去具体工作所属 WP）
* **WP-13**：无偿（域名续费）+ 非标（知识库内容、编辑、官网、白皮书）
* **WP-5**：标准（拍卖/公众号按次按篇）+ 非标（其他）
* **WP-2**：标准 5h/节点，但"安全事件响应、特殊故障响应"是否可额外报非标，无说明

结论：**标准/非标必须细化到"工作项"粒度**，每个工作项明确标注性质与统计责任方。

#### 1.4 上报格式不统一，可追溯性差

* 头部称谓五花八门："Wh 报告 / 非标工作量上报 / 非标工时报告"
* WP 简称混乱："WP-13 网站" vs "WP-13 白皮书和网站"、"WP-15 治理" vs "WP-15 核心治理工具集开发"
* 日期格式不一：`1.8` / `2025.1.10` / `2026-01-05`
* 绝大多数上报**不带产出物链接**（PR/issue/文档），统计员核验只能靠记忆与翻仓库

#### 1.5 统计表模板有缺口，统计员无操作指引

* 月度表只有 8 个 WP 列（WP-1/2/3/6/7/8/13/15），缺 WP-4/5/10/11/12/14/16；当月有这些 WP 的贡献时怎么处理（加列？折叠？）无规则
* 标准工时的数据来源（多签名单、issue #2 节点统计表、WP-4 JTI 数据、链上签到、open-meetings 纪要）未集中列明，全靠统计员摸索
* 三层把关机制提到"项目经理"，但**哪个 repo 的 maintainer 对应哪个 WP 未定义**

#### 1.6 流程规则缺失

* 非标上报截止时间未写明（rev7 只说"月初群通知"）
* 上报的最小颗粒、合并规则（同一日期多项可否合并）、补报规则（只写了"过期不补报"）不细

### 二、优化目标与原则

1. **规范 + 指引双重属性**：文档既定义规则，也是贡献者（怎么报）与统计员（怎么汇总）的操作手册。
2. **颗粒度细化到工作项**：每项工作都回答 5 个问题——做什么？产出物在哪？归哪个 WP？要不要自己报？统计员怎么核？
3. **消除矛盾**：spec 表述、统计表列名、社区实践三者对齐。
4. **模板化、机器可读**：统一上报格式并强制产出物链接，为 AI Agent 辅助统计（Issue #76 方案三）打基础。

### 四、各 WP 详表统一模板（核心机制）

每个 WP 一律改为如下两张子表：

**表 A：标准工作清单（无需自行上报，统计员自动/主动统计）**

| 工作项 | 产出物/数据位置 | 激励标准 | 统计方式 | 核验依据 |
| --- | --- | --- | --- | --- |
| 例：多签签名响应 | 链上多签交易 | 0.5h/月/钱包 | 委员会按名单统计 | 链上多签记录 |

**表 B：非标工作范围（需自主上报）**

| 工作类型 | 产出物 repo/位置 | 上报 issue | 质量要求 |
| --- | --- | --- | --- |
| 例：治理合约开发 | Jouleverse/governance | #15 | critical bug = 0 |

关键修订点（解决第一节矛盾）：

1. **WP-13 知识库规则修订**：知识库（how.jouleverse.com / wiki.jouleverse.com，repo 注明 `Jouleverse/how` 与 `Jouleverse/wiki` 两个）的**内容贡献、功能开发、编辑 review/merge** 一律归 WP-13，删去"内容贡献计入具体工作所属 WP"的旧表述（与社区实践对齐）。
2. **WP-7 与 WP-13 划界**：链上链代码、节点 repo、审计 repo 的开发 → WP-7；一切 wiki/知识库/网站/白皮书内容 → WP-13。
3. **WP-15 范围明确**：治理合约（多签/Wrapper/veJ/timelock/Governance）、治理机制研究与**提案（JIP/JEEP 等）**、genesis treasury & tokenomics 文档记账 → WP-15。
4. **WP-3 范围明确**：统计执行轮值 → 标准；PoWh 工具开发、规范修订 → 非标（报 issue #3）。
5. **统计表列名**：统一为 "WP-7 链代码开发"，与 spec 一致。

### 五、非标上报统一模板

```text
教链（J-25）2026.7月非标工时报告：

WP-15 核心治理工具集开发：(总计: 4h)
- 2026.7.21 4h: JIP-6 + JEEP-7 提案撰写 + ENS 架构调研
  [jips#6](https://github.com/Jouleverse/jips/issues/6) [jips#7](https://github.com/Jouleverse/jips/issues/7)

总计：XXh

```

规则：

* 头部固定：`{昵称}（{Core ID}）{YYYY.M}月非标工时报告`
* 每 WP 一段：`WP-{N} {全名}：(总计: Xh)`，全名取 spec 中的标准名，禁止简称
* 每行：`YYYY.M.D Xh: 简述` + 产出物链接（PR/issue/文档/链上记录，必填）
* 最小精度 0.5h；当期报当期；只报生产性时间
* 发到对应 WP 的 issue 评论区

## 会议发言纪要

### 一、 教链 J-25 发言纪要
1.  **近期工作进展**
    *   指导“大白”推进区块链浏览器的重构工作。
    *   安排“小新”对部分文档进行审阅（review）并输出方案草稿。

2.  **关于工作包（WP）说明书改进文档（核心议题）**
    *   **改进动因**：源于“小新”和“大白”在实际统计工作中发现的问题，是基于实践总结出的真实痛点。
    *   **核心原则（标准化与AI化）**：
        *   **目标**：所有工作最终应实现全AI化，减少人工上报和统计。
        *   **标准尺度**：规范化的程度应以 **“AI能正确识别和解析所需内容”** 为准，不必追求绝对的人为统一。
        *   **示例说明**：工作包的中文名称不必强制唯一，但编号（如wp-15）必须准确，因为AI主要依赖编号进行统计。
    *   **文档维护方式**：将文档视为代码仓库进行维护。有权限的维护者（如教链、Koant等）可合并修改，任何成员都可以提交PR（Pull Request）提出修改建议。
    *   **关于截止日期**：指出文档中“非标上报截止日期建议每月5号”是笔误，正确的截止日期应为**每月15号**（现行规则）。

3.  **关于生态激励与发展（回应微尘提问）**
    *   **基金会与链的关系**：基金会是独立于链的自治组织，链本身没有中心化管理机构。链只负责按规则释放核心激励和生态激励。
    *   **生态发展模式**：生态发展由社区成员驱动。任何成员若对生态发展有想法，可以**发起治理提案**，进行链上投票。获得共识后，可成立新的基金或激励计划，并获得链上拨付的预算（Joule）。
    *   **开发者持有燃料（Gas）的必要性**：开发者需持有一定量的Joule作为Gas，这是进行区块链开发的基本前提（类比以太坊）。获取方式可以是联系其他持有者（借/买），或通过参与核心贡献获得奖励。
    *   **关于“激励池”设想**：不赞同无责任方、无条件发放激励的“池子”模式。无人负责的激励等同于无效发放，会损害所有持币者的利益。对于日常测试用的少量Gas，**通过“水龙头”（Faucet）领取即可**。
